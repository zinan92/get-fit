# 轻练：到第一个真实客户能用上的最短路径（对 V1 试用规格的增量）

Status: **draft — 等 Park 审阅**，审阅通过前不拆 issue。

本文件不是平行规格。`docs/specs/2026-08-28-fit-plan-v1-real-client-pilot.md`（下称 V1 规格）仍是合同主体：用户故事、禁区、测试决策、Out of scope 全部继续有效。本文件只记录 08-28 之后变了什么、V1 规格哪些条款被替换，以及重排后的最短路径。

## 1. 自 08-28 以来变了什么

| 事实 | 对路径的影响 |
|---|---|
| v3 视觉（带脸的动作/食物角色、歪框打卡、训练橙/饮食绿）已落在网页端并部署；Park 定调产品价值是情绪价值 | 小程序客户端必须是 v3，不能是现有 WXML 工具人版本 |
| 认证旁路已关闭（DEV_MODE 身份只由服务端决定） | 无 |
| Sites 是 owner-only 私有托管，本机无部署凭据 | Sites 不可能是客户入口，**也不是教练入口**——教练朋友登不上 |
| 核实：小程序备案卡的是上架，不卡开发版/体验版；个人主体可有 15 名体验成员 | 首个试点（1 教练 + 1 客户 + Park）**不需要小程序备案，也不需要等个体户执照** |
| 核实：`wx.request` 的服务器域名必须 HTTPS + ICP 备案；体验版在手机上同样校验，只有打开调试模式才跳过 | 自有域名路线（Cloudflare Worker 直连）在备案前走不通；**云开发 `wx.cloud.callFunction` 不需要服务器域名，是备案前唯一干净的路** |
| 核实：云开发每个账号一个免费体验环境；上线后 15 天内须转付费（个人版 ¥19.9/月） | 试点期费用 ¥0 |

### 更正（Wendy 此前的判断）

我在 2026-09-14 的评估页里写过「门 #2：域名备案 + 小程序主体资质，卡在执照，周期以周计，越早启动越好」。这条对首个试点是错的：体验版不需要小程序备案，个人主体即可；域名备案只在「自建 API 域名」这条路上才是门，而本规格推荐的云开发路线不需要它。备案和执照仍是**正式上架**的门，但不在首客最短路径上。

## 2. 被替换的 V1 规格条款

| V1 规格原文（位置） | 替换为 |
|---|---|
| AC2 / Generation and review：「教练确认资料后可以明确触发本机 Codex CLI 生成」 | 试点期由**操作员**（Wendy，在 Mac mini 上）运行生成脚本；教练只确认资料、审草案、发布。ADR 0002 需修订为「operator-run」（待 Park 决定 D3） |
| AC4：「每个动作可查看 GIF」 | 每个动作显示 v3 角色插画 + 目标肌群 + 器械 + 中文要领；客户端不使用 GIF |
| Identity and access：「server-side WeChat code exchange」 | 身份来自云函数 `cloud.getWXContext().OPENID`（平台验证），试点后端不持有 AppSecret |
| Identity / Platform gates：「A separate approved customer API origin is required」 | 不需要 API origin；客户与教练都经 `wx.cloud.callFunction` 进入。ADR 0003 的**权限分离**仍成立：同一云函数内客户与教练走各自的授权检查 |
| In scope：「本地内存适配器与持久化 D1 适配器的同一页面服务契约」 | 内存适配器 + 云开发数据库适配器，契约测试不变 |
| Product and lifecycle：「more visual polish is deferred」 | v3 视觉是试点准入条件，不是后续打磨 |
| 教练工作台 = 私有 Sites（隐含） | 教练模式在小程序内，按 OPENID 白名单授权（待 Park 决定 D4） |

AC1、AC3、AC5、AC6 不变。AC7 的「教练从资料确认到发布 ≤15 分钟」只计教练本人操作时间，操作员生成在教练审阅之前完成。

## 3. 需要 Park 决定

- **D1 后端落点** — 推荐 **C：迁到微信云开发**。现有后端共 1127 行，只用 Web 标准 API（Request/Response、crypto.subtle），领域逻辑和 plan 校验可原样放进云函数，只换存储适配器和身份来源。备选 B：云函数做薄代理转发到公网 Cloudflare Worker——保留现有部署，但要新建一个公开 Worker、客户健康数据出境、两套系统一起运维，不推荐。
- **D2 小程序主体** — 推荐 **新注册一个个人主体小程序「轻练」**：个人身份认证即可注册、与星球隔离、15 名体验成员够试点。正式上架时再迁到个体户主体（换主体需走迁移流程，届时评估）。备选：等执照后直接用个体户主体；或挂在已有主体下。
- **D3 试点期谁运行生成** — 推荐 **操作员 = Wendy，在 Mac mini 上跑**（本机已有 Codex CLI 0.154、云开发 CLI、微信开发者工具），一客户一次。教练和 Park 都不用碰 CLI。第二个客户前再做可信生成网关（mingyu 模式，需单独运行时合同）。
- **D4 教练在哪审阅发布** — 推荐 **小程序内教练模式**：教练看到的草案就是客户将看到的 v3 页面，确认即发布；结构性修改（换动作/换餐）试点期由教练在微信里告诉操作员，操作员改完再让教练确认。备选：云开发静态托管网页工作台（星球模式），可做完整编辑，但要另做登录。

## 4. 最短路径

阻塞关系：S0 与 S1–S4 并行；S1 阻塞 S2/S3/S4 的真机联调；S5 需要全部完成。

### S0 平台门（Park 本人，`blocked-external`）

- 注册个人主体小程序，拿到 AppID；开通云开发免费体验环境。
- 把教练朋友和首位客户加为体验成员。
- 开发者工具用 Park 的微信扫码登录一次（Mac mini 上已装），供上传体验版；云开发 CLI 同样需要 Park 授权登录一次。
- 证据：后台截图（隐去 AppID/环境 ID）。AppID、AppSecret、环境 ID 不进仓库、issue、日志。

### S1 后端落云开发（M）

- Outcome：领域 handlers 在云函数中运行，客户与教练身份来自 OPENID，数据落云开发数据库。
- 验收：
  1. 现有 API/契约/持久化测试在云开发存储适配器上全部通过（fake 适配器 + 同一契约）。
  2. 身份只取 `getWXContext().OPENID`；请求体里的任何身份字段被忽略，有回归测试。
  3. 教练操作要求 OPENID 在教练白名单中；客户读写只能触达自己的数据。
  4. 快照写入带版本号，冲突时拒绝而非静默覆盖。
  5. 「打开天数」成为一等数据（每客户每天一条），不再从截断的审计日志推算。
  6. 云函数健康检查可独立回读（与「代码已上传」分开记录证据）。
- In：云函数入口、云开发存储适配器、身份与白名单、openedDays。Out：按实体拆集合、生成网关、提醒推送。
- 禁区：不把 DEV_MODE 类开关带进云函数；敏感快照继续加密；不记录原始健康值。

### S2 客户端 v3（M）

- Outcome：客户在小程序里看到与 `design/fit-plan-v3.html` 一致的邀请/同意/建档/今天/日历/打卡/反馈。
- 验收：
  1. 今天页信息结构与 v3 一致：训练在前、餐次在后，每项食物 kcal、餐次合计、当日合计。
  2. 打卡框默认歪着，点击后弹正（WXSS 动画，尊重系统减少动效）。
  3. 动作角色用 view + WXSS 绘制；食物角色试点期用静态 SVG/PNG 经 `<image>` 显示（`<image>` 内 SVG 不支持 `<style>` 和百分比单位，食物动画放到后续）。
  4. 只出现训练橙和饮食绿两个语义色；数字用 Fredoka（小程序加载字体的方式在 S2 开工第一天验证，不行则退回系统圆体数字）；无 emoji/箭头类字符。
  5. 客户侧不出现草案、模型、provider、prompt 字样（沿用现有渲染断言）。
- Out：换动作/换餐、提醒订阅、照片。

### S3 教练模式（S–M，依 D4）

- Outcome：教练在自己的微信里完成：邀请客户 → 确认资料 → 预览草案（客户视角）→ 发布 → 处理疼痛告警。
- 验收：非白名单 OPENID 看不到教练入口且接口拒绝；发布后客户端立即可读；草案预览复用客户端组件，不另画一套。
- Out：教练端结构化编辑（D4 选网页工作台时改由 S3' 承接）。

### S4 生成操作员流程与首批内容（S + 内容）

- Outcome：操作员一条命令为指定客户生成草案并导入，教练在小程序里看到。
- 验收：脱敏输入经云函数取出；Codex CLI 输出经 `plan.v1` 校验后以草案导入；失败不影响已发布版本；全程无原始 prompt/completion 落库。
- 内容：动作目录从 3 个扩到足够排 30 天（估 15–20 个），食物从 12 种扩到约 25–30 种，要领用教练的话术；由教练朋友提供，Wendy 录入并补角色插画。

### S5 证据门（Park + 教练 + 客户）

沿用 wechat-xingqiu 的规矩：**代码已上传、云函数健康、手机实测是三种不同证据，不能互相替代**。

1. 开发者工具上传体验版（记录版本号）。
2. Park 与教练用真机各走一遍完整流程。
3. 首位低风险成年客户七天试用，按 V1 AC7 回读：打开 ≥5 天、打卡 ≥3 次、教练发布 ≤15 分钟、疼痛告警全部处理。

## 5. 雷区（不挡首客，挡第二个客户）

- `hasManualRisk`：任何非空伤病标记都会让生成 409。首客按 ADR 0001 选无伤病客户即可；若客户报了「膝盖不适」之类小问题，需要把分级处理提前（轻微 → 按目录禁忌逐项屏蔽，严重 → 人工）。
- 生成依赖本机 CLI：一客户一次可接受，第二位教练或客户数增长前需要可信生成网关。
- 单快照并发：S1 已加版本冲突拒绝；多客户前再拆集合。
- 数据出境：云开发让健康数据留在境内；生成时脱敏档案仍会发给境外模型。上线前需要合规评估（非法律意见）。
- 800 kcal 固定下限、无训练频率校验：计划质量问题，教练审阅兜底，第二个客户前修。

## 6. 复用与偏离

- `zinan92/wechat-miniprogram-shipping`：按其 Plan → Build → CloudBase → Experience → Device Acceptance 模块推进；平台门记为 `blocked-external`；不存 AppID/AppSecret/环境 ID。
- `zinan92/wechat-xingqiu`：云开发小程序 + 开发者工具 CLI 上传体验版 + 三类证据分开的做法直接沿用。偏离：轻练试点不做云开发静态托管工作台（除非 D4 选网页）。
- `zinan92/mingyu-wechat-experience`：可信网关调用 Codex CLI 的模式留给第二个客户之后。
- Sites（fit-plan-mockup）：保留为网页演示和设计沙盒，不在试点数据链路上。
